# Техническое задание

D&D Character Companion - браузерное приложение для ведения персонажа по правилам D&D 5e 2014.

Это интерактивный помощник игрока: он считает параметры, отслеживает ресурсы и подсказывает, что можно сделать на текущем ходу. Это не декоративный лист персонажа и не сайт для чтения лора.

Источник правды по продукту: `Требования.md`. Этот файл требований не изменять. Если формулировка здесь расходится с требованиями, приоритет у `Требования.md`.

---

## 1. Цель и границы

### 1.1 Цель

Дать игроку за столом удобный инструмент, в котором:

- видны боевые параметры без лишних экранов;
- связанные значения пересчитываются сами;
- каждое сложное число можно раскрыть и понять;
- нельзя случайно потратить ресурс, которого нет.

### 1.2 Входит в объем

- ведение одного или нескольких персонажей;
- универсальное создание и ручное редактирование;
- расчеты по D&D 5e 2014;
- заклинания, ячейки, ресурсы, отдых;
- боевой режим и подсказка "что я могу сделать сейчас";
- инвентарь, экипировка, деньги;
- журнал кампании;
- сохранение в браузере, экспорт и импорт JSON.

### 1.3 Не входит в объем

- сервер, аккаунты, синхронизация между устройствами;
- броски кубиков и история бросков;
- анимации;
- правила D&D 2024 и любые самодельные правила;
- автоматический выбор вместо игрока там, где правила требуют решения.

## 2. Ограничения и правила продукта

- только браузер, без бэкенда и регистрации;
- ПК и телефон, адаптивный интерфейс;
- язык интерфейса: русский;
- расстояния показывать в метрах, не в футах;
- кубики бросает игрок сам, приложение только показывает формулу;
- данные персонажа живут в LocalStorage и сохраняются после каждого изменения;
- использовать только D&D 5e 2014; при расхождении с 2024 брать 2014;
- не придумывать значения, способности и взаимодействия;
- если механика не подтверждена имеющимися данными, явно обозначить пробел в коде и в интерфейсе, а не заполнять его догадкой.

Перевод футов в метры брать из русскоязычного справочника 2014, а не считать самостоятельно. Если точная формула перевода в данных не найдена, не подставлять свое значение: пометить пробел.

## 3. Стек и архитектура

### 3.1 Стек

Рекомендуемый стек:

- Vite;
- React;
- TypeScript;
- стили без анимаций, темная тема;
- данные правил в статических модулях или JSON.

Стек можно заменить на другой компонентный, если он лучше закрывает те же границы: отдельный слой расчетов, отдельные экраны, LocalStorage. Не собирать продукт одним монолитным компонентом.

### 3.2 Слои

Приложение делится на четыре слоя. UI не считает игровые формулы сам.

1. **Данные правил**  
   Справочники 2014: расы, классы, подклассы, заклинания, состояния, стандартные действия, предметы. Только достоверные записи. Неполные записи помечаются как неизвестные.

2. **Модель персонажа**  
   Состояние, которое хранится и редактируется: базовые характеристики, выборы игрока, текущие ресурсы, инвентарь, журнал.

3. **Движок расчетов**  
   Чистые функции. На вход: персонаж + правила + текущая экипировка. На выход: производные значения и разбор расчета для подсказки.

4. **Интерфейс**  
   Экраны, навигация, подтверждения, объяснения. Берет готовые числа из движка и не дублирует формулы.

### 3.3 Логические модули UI

| Модуль | Назначение |
| --- | --- |
| `CharacterSheet` | Главный экран с боевыми параметрами |
| `CharacterEditor` | Ручное редактирование |
| `CharacterCreator` | Пошаговое и быстрое создание |
| `StatsPanel` | Характеристики, навыки, спасброски |
| `CombatPanel` | Режим боя, ход, действия |
| `Spellbook` | Заклинания, в том числе доменные |
| `SpellSlots` | Ячейки заклинаний |
| `Inventory` | Предметы |
| `Equipment` | Экипированные вещи |
| `Resources` | Расходуемые ресурсы |
| `Journal` | Журнал кампании |
| `NPCList` | Знакомства |
| `QuestList` | Квесты |
| `RestManager` | Короткий и продолжительный отдых |
| `Conditions` | Состояния |
| `LevelUp` | Повышение уровня |
| `RulesExplanation` | Подсказки и разбор расчетов |
| `CharacterStorage` | Сохранение, сброс, экспорт, импорт |

Расчеты живут отдельно, например:

- `calculateAbilityModifier`
- `calculateProficiencyBonus`
- `calculateSpellSaveDC`
- `calculateSpellAttackBonus`
- `calculateArmorClass`
- `calculateSkillBonus`
- `calculateSavingThrow`
- `calculateMaxHP`

Одна формула - одно место. Компоненты только вызывают движок.

### 3.4 Навигация

На телефоне: нижняя навигация или столь же удобное меню. Крупные кнопки, мало мелкого текста.

На ПК: боковая навигация и более широкая сетка.

Быстрый доступ с телефона обязателен к HP, заклинаниям, боевой панели и инвентарю.

## 4. Модель данных

Ниже - минимальный состав. Поля можно уточнять при реализации, но смысл и обязательность сохранить.

### 4.1 Персонаж

Хранимые поля:

- имя;
- раса;
- класс;
- подкласс или домен;
- уровень от 1 до 20;
- предыстория;
- мировоззрение;
- заметки;
- базовые характеристики: сила, ловкость, телосложение, интеллект, мудрость, харизма;
- владения навыками и expertise, если применимо;
- владения спасбросками;
- владения броней, оружием, инструментами, языками и прочие;
- известные, доступные и подготовленные заклинания, включая cantrips;
- текущие ячейки заклинаний;
- текущие HP, временные HP, оставшиеся кости хитов;
- текущие ресурсы способностей;
- инвентарь, экипировка, деньги;
- состояния;
- журнал;
- расовые уточнения, если они нужны выбранной расе.

Для драконорожденного хранить родословную и тип дыхания. Для тестового персонажа: серебряный дракон, холод.

Производные поля не хранить как источник истины, а считать:

- модификаторы характеристик;
- бонус мастерства;
- AC;
- инициатива;
- скорость;
- максимальные HP, если их можно получить из правил и выборов игрока;
- пассивное восприятие;
- бонусы навыков и спасбросков;
- DC заклинаний и бонус атаки заклинанием;
- список атак из экипировки и способностей.

Если правило требует выбора игрока, например способ набора HP при повышении уровня, не подставлять скрытое решение. Показать выбор или дать ручной ввод и пересчитать остальное.

### 4.2 Предмет

- название;
- количество;
- вес;
- стоимость;
- описание;
- экипирован или нет;
- категория: оружие, броня, щит, расходуемые, магические предметы, инструменты, прочее.

### 4.3 Заклинание

- название;
- описание;
- уровень;
- школа;
- время накладывания;
- дальность;
- компоненты;
- длительность;
- концентрация;
- тип цели;
- требуемый спасбросок;
- нужен ли бросок атаки;
- эффект;
- масштабирование при ячейке выше уровнем.

У персонажа отдельно хранить, какие заклинания известны или доступны, какие подготовлены, какие являются cantrips, какие относятся к домену.

### 4.4 Журнал

- NPC: имя, где встретили, отношение, описание, важные факты, заметки;
- интересные факты: свободный текст;
- квесты: название, описание, статус, заметки;
- статусы квеста: активный, завершенный, проваленный, отложенный;
- локации: название, описание, NPC, события, заметки;
- общие заметки: свободный текст.

### 4.5 Боевое состояние сессии

Это состояние текущей игры, его тоже сохранять, чтобы не терять ход при обновлении страницы:

- доступность действия, бонусного действия, реакции;
- оставшееся перемещение текущего хода;
- текущая концентрация: название, длительность, краткое описание.

## 5. Система расчетов и объяснений

### 5.1 Принцип

Все, что можно вычислить из персонажа и правил, вычисляется автоматически. Пользователь не вводит руками бонус мастерства, модификатор характеристики, DC заклинания и подобные величины.

При изменении базового значения все зависимые параметры обновляются сразу. Пример: изменение мудрости жреца меняет DC, бонус атаки заклинанием и связанные навыки.

### 5.2 Обязательные расчеты

- модификатор характеристики по правилам 2014;
- бонус мастерства по уровню 1-20;
- класс брони с учетом экипировки;
- инициатива;
- скорость;
- максимальные HP по доступным правилам и явным выборам игрока;
- текущие и временные HP как введенное состояние;
- кости хитов;
- пассивное восприятие;
- бонус атаки оружия и заклинаний;
- шесть спасбросков;
- все навыки 2014.

### 5.3 Объяснение расчета

Это ключевая функция. У каждого сложного автоматического значения должна быть расшифровка простым языком.

Формат:

1. итог;
2. из каких частей он сложился;
3. арифметика.

Примеры из требований сохраняются по смыслу:

- модификатор мудрости +4 при значении 18: `(18 - 10) / 2 = +4`;
- DC спасброска заклинаний 15: `8 + бонус мастерства + модификатор мудрости`;
- бонус атаки заклинанием +7: `бонус мастерства + модификатор мудрости`;
- бонус атаки булавы +4: владение плюс сила.

Текст должен быть понятен человеку, который еще не знает правила наизусть. Не ограничиваться одними формулами без слов.

### 5.4 Подсказки по механикам

По нажатию на игровой термин показывать объяснение: атака, концентрация, бонусное действие, реакция, отдых и другие элементы интерфейса. Цель: приложение учит играть, а не только считает.

## 6. Функциональные требования

### 6.1 Характеристики

Показывать шесть характеристик: сила, ловкость, телосложение, интеллект, мудрость, харизма. Для каждой: базовое значение и модификатор. Модификатор считается автоматически.

### 6.2 Навыки

Показать все навыки 2014. Для каждого:

- название;
- связанная характеристика;
- итоговый бонус;
- есть ли владение;
- есть ли expertise, если применимо.

Бонус пересчитывать автоматически. По нажатию показывать расчет.

### 6.3 Спасброски

Показать все шесть спасбросков: модификатор характеристики, владение, итоговый бонус. Пересчет автоматический.

### 6.4 Владения

Отдельный раздел: броня, оружие, инструменты, языки, прочие владения.

### 6.5 HP

Крупный блок: текущие / максимальные, например `24 / 27`.

Кнопки:

- получить урон;
- получить лечение;
- добавить временные HP.

Изменение HP должно быть быстрым с телефона. Нельзя уйти в невозможное состояние без явного правила: например, текущие HP ниже нуля обрабатываются так, как это задано 2014, без самодельной логики. Если точное поведение при отрицательных HP в данных не закрыто, не выдумывать: ограничить ввод и пометить пробел.

### 6.6 Повышение уровня

Диапазон уровней: 1-20. Кнопка "Повысить уровень".

При повышении:

1. выставить новый уровень;
2. обновить бонус мастерства, если он изменился;
3. обновить доступные способности;
4. обновить ячейки заклинаний;
5. обновить остальные зависимые параметры;
6. показать, что изменилось;
7. если нужен выбор игрока, спросить его.

Не принимать решения за игрока.

### 6.7 Заклинания

Полноценный раздел книги заклинаний с полями из модели данных. Хранить известные и доступные, подготовленные, cantrips и заклинания по уровням.

### 6.8 Ячейки заклинаний

Показывать ячейки по уровням кружками или эквивалентным счетчиком, например `3 / 4`.

Действия:

- использовать ячейку;
- восстановить ячейки с подтверждением.

Нельзя потратить ячейку, которой нет. Набор ячеек зависит от класса и уровня по правилам 2014.

### 6.9 Домен Смерти

Отдельный визуально выделенный блок "Заклинания Домена Смерти". Доменные заклинания не смешивать с обычным списком так, чтобы их было не видно.

Отдельно показать способности домена, доступные на текущем уровне. Для каждой:

- название;
- уровень получения;
- описание;
- что нужно для использования;
- действие, бонусное действие, реакция или другое;
- ограничения;
- расходуемый ресурс, если есть.

Значения брать только из данных 2014.

### 6.10 Боевая панель

Отдельная вкладка или режим "Бой". Задача: не дать забыть порядок действий и ресурсы хода.

Показывать:

- действие: доступно / использовано;
- бонусное действие: доступно / использовано;
- реакция: доступна / использована;
- перемещение: сколько осталось на текущем ходу.

Использованное визуально отличать от доступного.

Кнопки:

- начать ход: сбросить действие, бонусное действие, реакцию и перемещение;
- закончить ход.

Нельзя потратить реакцию дважды и нельзя отметить действие использованным, если оно уже потрачено, без явного правила, которое это разрешает.

### 6.11 Действия в бою

В боевой панели показать доступные действия персонажа, включая стандартные 2014, которые к нему применимы:

- атака;
- наложение заклинания;
- рывок;
- отход;
- уклонение;
- помощь;
- подготовка;
- поиск;
- использование предмета;
- другие применимые стандартные действия.

При выборе показать коротко:

- что делает действие;
- что расходует;
- что будет после использования;
- варианты, если способов несколько.

### 6.12 "Что я могу сделать сейчас?"

В боевом режиме собрать понятный список текущего хода:

- действие: только доступные этому персонажу варианты;
- бонусное действие: только доступные;
- реакция: только доступные;
- перемещение: сколько осталось.

Список зависит от класса, способностей, экипировки и уже потраченных ресурсов хода.

### 6.13 Атаки

Раздел "Атаки". Для каждой атаки:

- название;
- тип;
- дистанция;
- бонус атаки;
- урон;
- тип урона;
- характеристики расчета;
- свойства оружия;
- описание.

Кубик не бросать. Показывать формулу, например `1d6 + 2 дробящего`. По нажатию на бонус атаки раскрывать расчет. Экипировка оружия меняет доступные атаки.

### 6.14 Концентрация

Если заклинание требует концентрации, явно показать блок концентрации:

- активное заклинание;
- длительность;
- краткое описание.

При попытке начать другое концентрационное заклинание показать предупреждение: новое заклинание прекратит текущую концентрацию. Без подтверждения старую концентрацию не сбрасывать.

### 6.15 Ресурсы

Отдельный блок. Отслеживать как минимум:

- ячейки заклинаний;
- Channel Divinity;
- ограниченные способности;
- прочие расходуемые ресурсы этого персонажа.

Для каждого: доступно / максимум, кнопки "Использовать" и "Восстановить". Если ресурс возвращается после короткого или продолжительного отдыха, это должно быть видно. Нельзя уйти ниже нуля.

### 6.16 Отдых

Два сценария: короткий отдых и продолжительный отдых.

Перед применением показать, какие ресурсы восстановятся по правилам. Восстанавливать только то, что правила 2014 действительно восстанавливают. Не восстанавливать остальное автоматически.

### 6.17 Состояния

Можно отметить состояния 2014, включая:

- ослеплен;
- очарован;
- оглушен;
- испуган;
- схвачен;
- невидим;
- парализован;
- отравлен;
- опрокинут;
- обездвижен;
- истощение;
- другие состояния 2014.

По выбору показывать описание по правилам. Не выдумывать текст состояния.

### 6.18 Драконорожденный

Для тестового персонажа реализовать особенности драконорожденного 2014. Отдельно показать "Драконье дыхание":

- тип: холод;
- область;
- спасбросок;
- урон;
- ограничение использования;
- восстановление.

Только значения из правил 2014.

### 6.19 Инвентарь, экипировка, деньги

Полноценный инвентарь с категориями из модели данных.

Отдельно показывать экипированные оружие, броню, щит и другие релевантные предметы.

Экипировка влияет на расчеты:

- броня и щит меняют AC;
- оружие меняет список атак.

Нельзя экипировать несовместимую вещь. Если совместимость в данных не определена, не угадывать: запретить опасное действие или пометить пробел.

Деньги отдельным блоком: медные, серебряные, электрумовые, золотые, платиновые. Количество меняется быстро.

### 6.20 Журнал персонажа

Раздел "Журнал" с подразделами: NPC и знакомства, интересные факты, квесты, локации, общие заметки. Поля и статусы по модели данных.

### 6.21 Создание персонажа

Кнопка "Создать персонажа".

Пошаговый сценарий:

1. имя;
2. раса;
3. класс;
4. подкласс;
5. уровень;
6. характеристики;
7. предыстория;
8. навыки;
9. владения;
10. снаряжение;
11. заклинания.

Также нужен быстрый путь: создать каркас и сразу править вручную.

### 6.22 Редактор персонажа

Все нужные значения редактируются. Автоматически вычисляемые поля не требуют ручного ввода. После правки базового значения зависимые поля пересчитываются.

### 6.23 Несколько персонажей

Поддержать список персонажей в LocalStorage: создание, выбор, редактирование. Если в текущей реализации удобнее начать с одного активного персонажа, список все равно не должен терять данные при создании нового без явного действия пользователя.

## 7. Интерфейс

### 7.1 Стиль

- dark fantasy;
- умеренная готика;
- современный UI;
- минимализм;
- высокая читаемость;
- удобство за игровым столом важнее декора.

Не делать визуальный перегруз. Не превращать продукт в фэнтезийный лендинг. Темная основа. Готические элементы умеренно. Без лишних рамок, градиентов, свечения и декора.

Анимации не нужны.

### 7.2 Главный экран

Сразу видны:

- HP;
- AC;
- инициатива;
- скорость;
- основные характеристики;
- бонус мастерства;
- DC заклинаний;
- бонус атаки заклинаниями;
- доступные ячейки;
- основные ресурсы;
- текущая концентрация;
- состояние текущего хода.

Базовые боевые параметры нельзя прятать за длинной цепочкой вкладок.

### 7.3 Мобильная версия

- удобная нижняя навигация или меню;
- крупные кнопки, нажимаемые пальцем;
- минимум мелкого текста и мелких элементов;
- быстрый доступ к HP, заклинаниям, бою и инвентарю.

### 7.4 Ошибки и подтверждения

Предотвращать невозможные действия:

- использовать отсутствующую ячейку;
- тратить ресурс, которого нет;
- потратить реакцию дважды;
- экипировать несовместимую вещь;
- выйти за значение, которое правила запрещают.

Для опасных действий показывать подтверждение: сброс данных, восстановление ячеек, срыв концентрации, удаление персонажа и аналогичные операции.

## 8. Хранение данных

- основное хранилище: LocalStorage;
- автосохранение после каждого изменения;
- после закрытия браузера персонаж остается;
- сброс данных только с подтверждением;
- экспорт и импорт JSON как резервная копия.

Формат JSON должен быть достаточно стабильным, чтобы импорт старой копии не ломал приложение молча. При несовместимой копии показать понятную ошибку.

## 9. Тестовые данные

При разработке использовать персонажа:

- класс: жрец;
- подкласс: Домен Смерти;
- уровень: 3;
- раса: драконорожденный;
- драконья родословная: серебряный дракон;
- тип дыхания: холод;
- правила: D&D 5e 2014.

Этот персонаж нужен как пример и как основной сценарий проверки: расчеты жреца, доменные заклинания, Channel Divinity, дыхание драконорожденного, боевая панель и отдых.

Конкретные числа способностей, слотов, HP и предметов брать из правил 2014 и из явного ввода тестового персонажа. Не подставлять "типичные" значения на глаз.

## 10. Пробелы в правилах

Если для механики не хватает достоверных данных 2014:

1. не выдумывать правило;
2. обозначить пробел в коде;
3. в интерфейсе показать, что значение неизвестно или недоступно;
4. спросить владельца проекта, а не закрывать дыру догадкой.

То же относится к неоднозначности правил. Не выбирать "более логичный" вариант 2024 и не смешивать редакции.

Неоднозначность UX, которая не меняет правила, решать в пользу самого простого и быстрого варианта за столом.

Не добавлять функции ради сложности.

## 11. Порядок разработки

Не писать весь продукт одним проходом. Сначала архитектура, затем слои по порядку:

13. редактор персонажа;

15. полировка UI и адаптивности.

После каждого крупного этапа проверять, что уже сделанное не сломалось.

Перед кодом этого ТЗ достаточно как согласованной архитектуры. Реализацию начинать с пунктов 1-4, а не с визуала.

## 12. Критерии приемки

Работа считается соответствующей требованиям, если:

- приложение открывается в браузере без сервера и без регистрации;
- интерфейс на русском и удобен на ПК и телефоне;
- тестовый жрец 3 уровня с Доменом Смерти и серебряным драконорожденным собирается и сохраняется;
- связанные параметры пересчитываются без ручного дублирования формул;
- у сложных значений есть человекочитаемый разбор расчета;
- кубики не бросаются;
- используются только правила 2014, без самодельных механик;
- ячейки, ресурсы и действия хода нельзя потратить сверх доступного;
- концентрация, отдых и экипировка ведут себя по требованиям выше;
- данные переживают перезагрузку страницы и выгружаются в JSON;
- главный экран показывает боевые параметры без лишней навигации.

Если пункт нельзя закрыть из-за отсутствия данных 2014, он не реализуется "примерно": показывается как пробел.
